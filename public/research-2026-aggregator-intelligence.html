Aggregation Control Plane

One governed connection and normalization layer for models, tools, SaaS systems, data, payments, commerce, social, media, logistics and vertical-industry providers.

Research boundary: this page does not enable a provider, install a dependency, grant agent authority, activate payment rails or count an external catalog as a SONARA-native integration.

Architecture decision

SONARA should build one shared Aggregation Control Plane in SONARA One, then expose domain-specific connection experiences through Business Builder™, Creator Studio™ and Growth Studio™.

tenant → connection → capability class → capability → policy → adapter → normalization → durable workflow/event → evidence → reconciliation → telemetry

Build-vs-buy boundary: SONARA owns tenant authority, canonical state, workflows, evidence, reconciliation, telemetry and billing. Provider breadth stays replaceable behind adapters.

For external writes: desired state → authority classification → approval when required → idempotent provider call → receipt → reconciliation → settled state.

What the control plane owns

  • Tenant-scoped connections, external account identity and granted scopes.
  • Credential references without exposing raw secrets to clients, models or telemetry.
  • Per-connection capability negotiation instead of a generic connected/not-connected flag.
  • Canonical SONARA records plus provider IDs, versions, provenance and extension envelopes.
  • Webhooks, incremental cursors, replay protection, retries, dead letters and reconciliation.
  • Rate, quota, concurrency, latency and monetary budgets.
  • Human approval for sensitive financial, destructive, publication, security, legal or bulk actions.
  • Provider health, circuit breakers, degradation and setup-required states.
  • OpenTelemetry correlation by tenant, capability, provider, latency, cost and outcome.

Aggregator capability classes

A connection is not a capability. SONARA separates managed auth, bounded reads, cursor sync, event ingress, synchronous actions, durable tasks, bidirectional reconciliation, policy routing, regulated mutations and safety-gated device commands.

Truthful connection states

Do not reduce a connection to a green checkmark. A provider/account should report capability and operating state such as connected, limited, degraded, setup required, reauthorization required, rate limited, budget blocked, disabled or unavailable, with last sync and last reconciliation evidence.

Deterministic formulas

Aggregation readiness: 0.20*canonical_model + 0.15*auth_scope + 0.15*events + 0.15*reconciliation + 0.10*observability + 0.15*failure_handling + 0.10*capability_negotiation

Provider route score after hard policy constraints: 0.25*quality + 0.25*reliability + 0.15*freshness + 0.10*latency_fit + 0.10*cost_fit + 0.15*policy_fit

Hard constraints such as tenant authorization, data residency, capability support, legal boundaries, approval requirements and budget ceilings run before any score.

Native integration proof

A provider counts as a verified SONARA-native connector only after its exact auth flow, scopes, canonical mapping, sync/webhook behavior, tenant isolation, failures and rate limits, secret boundary, telemetry, reconciliation, sandbox evidence, one-tenant canary and production evidence all pass.

Research catalogs, compatible SDKs and third-party unified-API catalogs do not count as native SONARA coverage.

Verified connector depth is now the engineering priority

Architecture breadth is no longer the primary gap. SONARA should measure each connector through evidence stages: research only → adapter contract → sandbox verified → tenant canary verified → production verified.

A connector does not count as verified because an SDK exists, OAuth opens, a third-party catalog lists it, or one request returned successfully. Production verification requires tenant isolation, scoped credentials, capability negotiation, sync/event correctness, reconciliation, failure handling, observability, one-tenant canary evidence, rollback, deletion/disconnect proof and exact live-SHA evidence.

The target is not a huge unverified connector catalog. The target is a smaller set of deeply verified connectors whose authorization, synchronization, provider receipts, recovery and production behavior can be proven.

First production canary

Start with a read-only SaaS/Data Connection Aggregator for one tenant, one low-risk provider and one canonical object type. Prove credential isolation, incremental cursors, webhook handling when available, health, backoff, provenance, OpenTelemetry, reconciliation and disconnect/data-deletion behavior before attempting money movement, banking mutations, publication writes or broad multi-provider routing.
