One shell, multiple work surfaces

SONARA should not become one overloaded universal dashboard. The stronger frontend is one recognizable shell and token system that composes task-specific workspaces: business operations, records, customers, agents, evidence, schedule, POS, kiosk, kitchen, field service, fleet, commerce, creator media, analytics and spatial work.

2026 market signal

Current high-traffic web and app-store patterns concentrate attention around search, video, social, AI assistants, communication, files, identity, jobs, delivery, POS and creator tools. The design implication is task continuity: fast search, clear state, persistent context and adaptive navigation matter more than decorative dashboard density.

Visual operating rule

Cinematic presentation belongs in marketing, startup and information-bearing media/spatial experiences. Work surfaces remain calm and operational. Translucent material effects are reserved for navigation and control layers; tables, forms, evidence, receipts, tickets and long text remain opaque enough for fast scanning.

Agentic UI boundary

Intent-composed interfaces may select from SONARA-owned semantic components only after deterministic validation. Model output is not permission. Arbitrary model-authored JavaScript, privileged HTML, hidden destructive actions, payment authority and arbitrary external destinations stay outside the accepted UI contract.

Accessibility + input

SONARA keeps a 44 CSS-pixel default interactive target and larger high-touch modes. Sticky content must not hide keyboard focus. Drag-and-drop workflows require a non-drag alternative. Maps need list equivalents. Charts need textual or tabular equivalents. Motion and sound remain reducible or user-controlled.

Performance budget

Current Core Web Vitals good-experience targets are LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1. Visual polish must fit inside those loading, responsiveness and stability budgets rather than compete with them.

Current implementation direction

  1. Use the existing Nexus v3 and Evergreen Operations token authority.
  2. Standardize surface archetypes and state vocabulary.
  3. Adopt reusable operational shell primitives without a framework migration.
  4. Expose agent, RAG, tool, approval, offline, stale, sync and failure truth.
  5. Strengthen mobile, field, POS, kitchen and kiosk modes.
  6. Add browser-level visual/keyboard regression only after dependency review.
  7. Add compositional/generative UI only after a semantic component contract and deterministic policy gate exist.
  8. Use 3D/AR only when the domain itself benefits from spatial information.

Open-source reference boundary

shadcn/ui, Radix Primitives, Fluent UI, Storybook, Playwright and axe-core are recorded as frontend research or future tooling candidates. None are installed or granted production authority by this pass.

Pass #2: agentic and adaptive UI direction

2026 market evidence strengthens five frontend rules: AI belongs inside task workflows rather than replacing them; tool execution and approval state must be visible; design-system context should be machine-readable for coding agents; responsive behavior should be component-aware; and cinematic motion or 3D must remain progressive enhancement.

  • Agent actions: direct only when low-risk and reversible; preview or explicit approval when external, irreversible, financial, destructive, or authority-changing.
  • Collections: compact screens prioritize list/detail, larger screens retain tables, and large datasets switch to virtualization or server pagination rather than rendering everything.
  • 3D/WebGPU: use only when spatial information matters, and always provide a useful compatible or 2D fallback.
  • Design-to-code: tokens, components, states, accessibility, and deprecated patterns are engineering context for people and agents.
