## Executive decision

Build **SONARA Studio as a unified workspace inside Creator Studio**, not as a fourth top-level product.

SONARA Industries remains the parent, SONARA One remains the shared platform, and the three public products remain Business Builder, Creator Studio, and Growth Studio.

The Studio should unify:

- scripts, documents, books, lyrics, captions, prompts, translations, and metadata;
- images, design, thumbnails, campaign assets, and product imagery;
- video editing, transcript editing, captions, generative B-roll, shot planning, and exports;
- music, audio, podcasting, voice, sound effects, stems, and release packaging;
- live review, comments, approvals, versions, and client handoff;
- publishing/export adapters for social and distribution channels;
- rights, consent, provenance, licenses, and audit evidence;
- performance analytics and revenue attribution;
- deterministic workflows plus bounded agent skills;
- future 3D, AR, game-production, and workstation companion workflows.

Do **not** attempt to recreate Premiere, After Effects, Pro Tools, AutoCAD, Blender, Unreal Engine, Salesforce, Shopify, Toast, Procore, ServiceTitan, and every vertical ERP inside the Express web process. SONARA's advantage should be a shared control plane, common records, approvals, entitlements, automation, knowledge, and adapters.

## Agentic architecture

SONARA should use a four-layer model:

1. **Reasoning** — LLM or deterministic planner proposes a plan.
2. **Skills** — discrete capabilities with schemas, permissions, costs, and safety classes.
3. **Workflow engine** — deterministic steps, retries, idempotency, timers, queues, stop/approve states.
4. **Adapters** — actual provider/database/payment/social/media operations.

Agents never receive raw unrestricted access to databases, shell, provider credentials, payment authority, social publishing, or destructive actions.

## Deterministic workflows and formulas

### Idempotency key

For any external side effect:

```text
idempotency_key = SHA256(
  organization_id
  + workflow_type
  + canonical_business_object_id
  + intended_action_version
)
```

The exact canonicalization format must be defined and tested per workflow.

### Retry policy

Use bounded exponential backoff with jitter. Example planning formula:

```text
delay_n = min(max_delay, base_delay * 2^attempt) + jitter
```

Retries must distinguish transient provider failure from validation, permissions, insufficient funds, policy rejection, and permanent input errors.

### Job priority

Use a transparent score, not LLM intuition:

```text
priority =
  customer_tier_weight
  + deadline_weight
  + interactive_weight
  + age_weight
  - estimated_resource_cost_weight
```

Cap every component so one field cannot starve the queue.

### Media cost budget

Before dispatch:

```text
estimated_job_cost =
  provider_unit_cost
  * requested_units
  + storage_estimate
  + worker_estimate
  + safety_margin
```

Reserve usage before running expensive work and settle against actual usage when completed.

### RAG retrieval

Use hybrid retrieval:

```text
candidate_score =
  alpha * vector_score
  + beta * lexical_score
  + gamma * freshness_score
  + delta * authority_score
```

Tenant/ACL filters happen **before** retrieval/ranking. Do not retrieve globally and filter afterward.

## Workflow durability

Temporal is a useful architecture reference for durable execution because it persists workflow state and provides retries, timers, signals, and recoverability. Do not add Temporal merely because it is popular. First benchmark the actual gaps in SONARA's event-outbox/consumer design.

Source:
- https://temporal.io/

Decision gate:

- If existing SONARA event consumers can prove idempotency, durable state, retries/backoff, dead letters, cancellation, timers, human suspension/resume, concurrency safety, replay, and observability at the required scale, keep the simpler system.
- If those capabilities become expensive or brittle to maintain, evaluate an isolated Temporal service with a separate architecture decision.

## MCP and tool interoperability

The MCP 2026-07-28 specification adds a stateless protocol core, multi-round-trip requests, header-based routing, cacheable list results, authorization hardening, and extensions.

Source:
- https://blog.modelcontextprotocol.io/posts/2026-07-28/

SONARA should use MCP as a connector/interoperability pattern, not as an authority bypass. A connected MCP server never automatically gains:

- service-role credentials;
- customer-wide data;
- shell access;
- payments;
- publishing rights;
- destructive actions.

Every MCP tool must map into the same skill/permission/audit/approval system as native adapters.
